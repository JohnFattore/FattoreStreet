## Overview

`django/chatbot/` is a small app, but it packs together two ideas worth understanding on their own: (1) the Gemini API (`google-genai`) is stateless per HTTP request — there's no server-side session — so every call to `ChatbotView.post()` has to manually reconstruct the last 10 turns of conversation as a `history` list before it can call `chat_session.send_message()`, and it does this by re-querying the `Interaction` table and replaying rows back into `types.Content` objects; and (2) the `Interaction` model is versioned by `django-simple-history`'s `HistoricalRecords()` field, which auto-generates a parallel `HistoricalInteraction` table and a `post_save`/`post_delete` signal that snapshots every row change — a very different, framework-driven approach to audit-trail than anything else in this repo (Spring Boot's entities have no equivalent, and other Django apps like `portfolio` don't use it either). Both mechanisms are common patterns worth recognizing elsewhere: "replay stored rows into an external stateless API's expected shape" and "get an audit table for free via a model field instead of hand-rolled logging."

## Questions to work through while reading

Why does the code query `order_by('-timestamp')[:10]` (descending) instead of `order_by('timestamp')[:10]` (ascending) directly — what would go wrong with the latter if a user had more than 10 total interactions?
2. `chat_session` is created fresh on every single `POST` (line 53), fully rehydrated from the DB each time, then discarded when the request ends. What would change, functionally or performance-wise, if the app instead tried to keep `chat_session` objects alive across requests (e.g., cached per-user in Redis or an in-memory dict)? What problem is the "rebuild from DB every time" approach avoiding by *not* doing that?
3. `HistoricalRecords()` hooks into Django's `post_save`/`post_delete` signals to write to `HistoricalInteraction` automatically. If the interaction-saving line (`Interaction.objects.create(...)`, line 65) were changed to a bulk operation like `Interaction.objects.bulk_create([...])`, would the historical row still get created? (Check simple-history's documented signal-based limitation with bulk operations, then confirm which code path this view actually uses.)
4. The `HistoricalInteraction` migration shows `history_user` as a nullable FK to `settings.AUTH_USER_MODEL`, separate from the `user` FK that's just copied from `Interaction`. What's the difference in *meaning* between `history_user` and `user` on a historical row — whose action does each one represent, and in this specific view, would they ever differ for a given interaction?
5. `principles.json` (141 lines of brokerage tables, tax account structures, etc.) is loaded once at import time and stuffed into `system_instruction` on literally every request, regardless of what the user's `message` actually asks about. What are the tradeoffs of this "always include the full static context" approach vs., say, retrieving only relevant sections based on the user's message (a lightweight RAG-style approach)? ## Primer: replaying persisted state into a stateless chat SDK, and signal-driven audit tables

**Stateless chat APIs and history replay.** Modern LLM chat SDKs (Gemini, OpenAI, Anthropic) are almost universally stateless at the HTTP layer: the server holds no memory of "this conversation" between calls unless you pass the whole conversation back in yourself. Client SDKs like `google-genai`'s `client.chats.create(history=...)` offer a convenience object that *feels* stateful (you call `.send_message()` repeatedly and it remembers), but that object only lives as long as your process/request does — it's a local convenience wrapper around "concatenate history + new message, send it all every time." Any app that wants conversations to survive across requests (as this one clearly intends, since users expect the bot to remember earlier turns) has to own persistence itself and rebuild the SDK's expected input shape from stored rows on each new request. The key design questions are always: how much history to replay (here, a hardcoded last 10), and how to shape stored rows into whatever alternating role/turn structure the SDK expects.

**Signal-driven audit tables (django-simple-history).** Rather than writing explicit "insert into an audit log" calls at every place a model changes, `django-simple-history` attaches to Django's model signals (`post_save`, `post_delete`, and `m2m_changed`) once via a model field (`HistoricalRecords()`) and a metaclass that walks the model's fields to auto-generate a shadow "Historical<Model>" table with the same columns plus versioning metadata (`history_type`, `history_date`, `history_user`). This trades explicitness (you can't see "an audit row gets written here" by reading the view code — it's invisible unless you know to look at the model definition) for consistency (it's structurally impossible to add a new field to `Interaction` and forget to log it, since the historical table mirrors the live one automatically) and for signal-based limitations (bulk operations that bypass `save()`/`delete()` don't fire the signals, so bulk-written or bulk-deleted rows silently get no history entry unless you use simple-history's dedicated bulk-history helpers).
