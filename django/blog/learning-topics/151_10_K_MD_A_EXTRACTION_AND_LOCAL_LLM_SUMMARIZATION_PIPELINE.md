# 10-K MD&A extraction and local-LLM summarization pipeline

_FattoreStreet @ [`d2356a6c`](https://github.com/JohnFattore/FattoreStreet/tree/d2356a6cfb4cd043332cb23119b4b062b080af50) — 2026-07-29_

_Source: [#151](https://github.com/JohnFattore/FattoreStreet/issues/151)_

## Overview

`FilingSummaryService` (`springboot/src/main/java/com/fattorestreet/sec_api/filing/FilingSummaryService.java`) is the one place in the codebase where Spring Boot calls out to the locally-hosted LLM (`llm/`) rather than just fetching structured SEC data. For every non-fund `Asset`, it walks the SEC `submissions` JSON for `10-K` filings, fetches the raw filing HTML from EDGAR, regex-extracts just the "Item 7. Management's Discussion and Analysis" section (stopping at "Item 8. Financial Statements"), truncates it to a word budget, and POSTs it to a local `llama-server` OpenAI-compatible endpoint for a ~200-word summary, which gets persisted as a `FilingSummary` row. It's worth understanding both halves: the fragile-but-effective plain-regex HTML/MD&A extraction (no HTML parser library, no LLM-based extraction — just anchored regexes and character-entity decoding), and the pattern of treating a self-hosted LLM as just another backend dependency with its own base URL, timeout, and failure mode. It's also a good example of a batch job that's resilient to partial failure per-ticker (each `Asset` is wrapped in its own try/catch so one bad filing doesn't kill the whole `summarizeAll()` run) and idempotent via a DB uniqueness constraint on `accession_number`, so re-running it after a partial failure just skips already-summarized filings instead of reprocessing them.

## Questions to answer while reading

1. Why does `extractMda` require the candidate MD&A section to be at least 1000 characters (line 213) before accepting a match, and why does it loop over *all* `ITEM7_START` matches (via `while (startMatcher.find())`) rather than just taking the first one?
2. `existsByAccessionNumber` is checked before the filing is even fetched (line 137), but `FilingSummary` rows are only inserted after a successful LLM call. Walk through what happens if `summarizeAll()` is interrupted (e.g., the process is killed) partway through a ticker with 3 unsummarized 10-Ks — what state is left in the database, and why does re-running produce the correct result without any manual cleanup?
3. `callLlm` swallows all exceptions and returns `null` (lines 244–252), which `summarizeForAsset` treats as "skip this filing" (line 159–162) rather than a fatal error. Contrast this with `summarizeAll`'s outer catch block (lines 93–99), which treats a different set of exceptions as fatal per-ticker but non-fatal overall. Why are LLM failures handled at a finer grain than, say, a malformed SEC submissions response?
4. The system prompt (lines 47–50) asks for "approximately 200 words" but `max_tokens` is capped at 350 (line 236) — why cap tokens well above the target word count instead of exactly at it, and what would happen to a summary if `max_tokens` were set too low relative to a verbose model response?
5. This is one of only a few places SEC filing text is truncated by a raw word count (`MAX_INPUT_WORDS = 1800`) rather than a proper tokenizer-aware budget. Given that `qwen2.5-7b-instruct` has a real context window, what could go wrong with word-count-based truncation for a filing written in a language or format where token-per-word ratios are unusually high (e.g., dense legal boilerplate, tables converted to text)?

## Primer: local LLMs as an ordinary backend dependency

The interesting architectural idea here isn't the regex extraction (that's a fairly standard "clean HTML, anchor on section headers" scrape) — it's that `FilingSummaryService` treats the local LLM exactly like it would treat any other internal HTTP service: a base URL (`llm.server.url`), a REST call with a JSON body, a timeout implicit in `RestTemplate`'s defaults, and a null-on-failure contract the caller has to handle. `llama.cpp`'s server mode exposes an OpenAI-compatible `/v1/chat/completions` endpoint specifically so that application code doesn't need a special SDK or client for a self-hosted model — the same request/response shape works whether the backend is OpenAI's API or a `.gguf` model file running on a GPU in the same container. This is a common pattern for teams that want to keep certain data (unpublished analysis, in this case a summarization step over public SEC text) off third-party AI APIs, or that want deterministic cost (a fixed GPU box instead of per-token billing) for a workload that's called in a scheduled batch rather than interactively. The tradeoff shows up directly in this file: no retries, no queueing, no circuit breaker — because the README says the server "processes one request at a time," any concurrency has to be handled by not building it, which is exactly what the sequential `for (Asset asset : assets)` loop in `summarizeAll` does.
